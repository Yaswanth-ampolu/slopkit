Slopkit Field Guide

Console-side gadget sweep, start to finish. Read this once before you touch anything.

Contents 0 — Safety (do first) 1 — Offline or online? 2 — Open the launcher 3 — Set the controls 4 — Run the sweep 5 — Read the result 6 — Out of memory? Auto Runner 7 — Harvest (online only) 8 — Use the file 9 — Troubleshooting

⚠ What this can and cannot do

This sweep reads memory and reports what it found. It does not write firmware, does not install anything, and cannot brick the console.

The realistic worst case is a kernel panic — a crash you clear by holding the power button. That is not a brick.

The thing that actually ends your jailbreak is a firmware update, not this tool. See step 0.

0Safety — do this first

Do these before touching the network

  1. Settings → System → System Software → Auto-Updates
    • Untick Download System Software Files Automatically
    • Untick Install System Software Automatically
  2. If you can: Settings → Network → Set Up Internet Connection → your network → Advanced → DNS Settings → point it at a filtering resolver (NextDNS, ControlD).
  3. Do not sign into PSN on this console.

If firmware 14.00 installs, it patches the kernel bug and there is no downgrade path. That ends the jailbreak permanently. This matters far more than any ban risk.

The status line turns green if the database is reachable. If it turns red, the dropdown switches itself to ntfy.sh — that is the sink that works on this console.

3Set the controls

Firmware: dropdown

Pick 13.60. If the page detected your User-Agent it is already set.

Memory: dropdown

Leave it at low (n=128).

  • Panics before any output? → drop to ultra-low (n=64), then emergency (n=32, full carrier)
  • Higher n is faster but uses more memory

Send findings to dropdown

Three choices: off, ntfy.sh and database.

  • off — nothing leaves the console. Use this if you are staying offline. You read results off the screen instead.
  • ntfy.sh — use this one. It sends the findings out so they can be collected without photographing anything.
  • database — the original path. It fails on this console; leave it alone.

Why ntfy works when the database does not. The database endpoint needs a special authentication header, and a custom header makes the browser send a permission request first. ntfy takes a plain POST with no special headers, so there is no permission step to fail. Same job, one less thing in the way.

Sweep gadgets from box

Leave the default 2B00000.

This sets wstart, which jumps the sweep start to webkitBase + 0x2B00000, skipping a region that was already found unreadable.

Gotcha: clearing the box does not mean "start from zero" — empty falls back to 2B00000. To genuinely start at zero, type 0.

4Run the sweep

Click Sweep gadgets.

That opens notify.html with:

?go=1&auto=1&fw=13.60&…&scan=1&lines=400&notaska=1&scanmb=8&wstart=0x2B00000

It then:

  1. Runs the notify proof to establish webkitBase and kernelBase
  2. Scans libkernel_web .text for syscall stubs
  3. Scans 8 MB of libSceNKWebKit .text for the 21 ROP gadgets

Watch the screen the whole time

Expect several minutes. Closing the tab loses the run. Do not touch the console while it works.

If you see SCAN-NOBASE, stop

Nothing downstream can help. The wall is the notify proof, not the tooling. The offsets in FW13_60_RAW are wrong and that is where the work is.

If you see SCAN-GADGET lines, you are through

Photograph the screen. That is the entire payload — you can stop here and never go online.

6Out of memory? Use the Auto Runner

If the notify proof works but everything else dies, this is your fix

That combination has one cause: the sweep is doing far too much work in a single page load. The proof needs a handful of reads. A full sweep needs tens of thousands.

Why it happens. A sweep covers a range of WebKit's code, reading it in 256-byte windows that advance 248 bytes at a time. Covering 8 MB that way is about 33,800 separate carrier reads in one page. The notification proof uses a few dozen. So the proof succeeds, and then the tab runs out of memory and the console throws a system error — not because anything is broken, but because the scan is simply too large for one run.

The fix: cut it into chunks. Each chunk is a separate page load, so memory starts clean every time. The Auto Runner does this for you and remembers where it got to.

0.25 MB per run is roughly 1,060 reads — small enough to finish.

  1. Open the Auto Runner autorun.html
  2. Set Chunk MB to 0.25 and Cover MB to 4. That is 16 short runs rather than one run that dies.
  3. Leave Sink on ntfy.sh and Memory on low. If a chunk still dies, drop Memory to ultra-low and lower Chunk MB to 0.25.
  4. Press Start the run and then do nothing. The page walks the range on its own: it opens the sweep, waits for the chunk to finish, returns, and starts the next one. A progress bar shows how far it has got.
  5. If it stops partway — a crash, or you closed it — just open the Auto Runner again and press Start. It resumes from the first unfinished chunk. Nothing already collected is lost.
  6. When it finishes, open the harvester, set source to ntfy.sh, and press Load findings. It stitches every chunk into one offset file.

Why this is safe

Smaller reads are gentler on the console than one large sweep, not more dangerous. A crash mid-chunk costs you that chunk and nothing else.

If you want to watch it work

Run one chunk by hand first, so you can see the lines go by. Set the launcher normally, then edit its URL and change scanmb=8 to scanmb=0.25. If that single small sweep completes and shows SCAN-DONE, the Auto Runner will work.

7Harvest — online only

Skip this entirely if you ran offline.

  1. Set Send findings to to ntfy.sh
  2. Click Sweep gadgets again — the findings now batch out to ntfy as they are produced
  3. If the sweep dies partway, switch to the Auto Runner (step 6) instead — it runs the same scan in chunks that survive
  4. When it finishes, click Harvest what the console uploaded →
  5. Set source to ntfy.sh
  6. Set topic / stream to ps5slopkit1360 — this is the topic name, not the old stream name
  7. Click Load findings

8Use the file

It fills the two tables 13.60.js currently leaves empty:

// Intentionally empty: fill from newer slopkit before use with old main.js.
let wk_gadgetmap = {};
let syscall_map = {};

Replace those two lines with the generated ones. Keep the existing FW13_60_RAW block above them — it holds the host-constructor candidates and the notify offset, which the sweep does not produce.

Sending a diagnostic

If something fails and you want it looked at, open netcheck.html, press Run the check, then press Send diagnostics. That posts the console's firmware, screen, user-agent and the reachability of every endpoint to the same topic the sweep uses, so it can be read from anywhere without photographing the screen. It is the single most useful thing to send when reporting a problem.

The check also settles the question of why one sink works and another does not: it runs each endpoint twice, once as a plain request and once with a custom header, so a difference between the two columns points straight at the cause.

The one thing that decides everything

Steps 0–5 are safe, offline and reversible. Step 6 is the only one that touches the network — and you can complete the entire technical goal without ever doing it.
